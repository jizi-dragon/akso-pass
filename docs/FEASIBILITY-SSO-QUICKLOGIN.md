# 快捷登录改走 SSO / AD 域：可行性与复杂度分析

> 状态：**分析稿**（未动任何代码）
> 分析对象：`akso-pass` v4.1.3（2026-10-12）
> 目标平台：Akso eGMP / 低代码平台（`tonbridge-config.aksoegmp.com`，内网形态 `http://10.100.0.105`）
> 触发问题：**模拟输入账密 + 点击登录**有时登不上（现象描述："密码还没填充，就点击登录了"）

---

## 0. 结论先行

| 问题 | 结论 |
|---|---|
| SSO 能否作为快捷登录的**主通道**？ | **不能（已按你的实际配置判定）**。配置实为"**跨域 IdP 委托**"型 OAuth2 授权码模式：授权中心＝外部 Authing，`AuthorizationCode` + `client_secret` 在**平台服务端**换票，回调落平台自己域。身份基准是 **Authing 的浏览器会话**（一个 profile 一份），而本扩展的全部价值建立在"同一窗口里 N 个身份同时有效"之上。二者架构互斥 —— 换过去不是"修好填表"，是**拆掉产品的立身之本**。且扩展的授权域护栏会在跳往 Authing 的那一刻**主动解绑页签**（代码实锤，§3.3 断点 B）。 |
| AD 域能否作为主通道？ | **更不行**。AD/IWA 的身份基准是 **Windows 登录会话**——一台机器一个，连"选人"的入口都没有。 |
| SSO 有没有值得做的子集？ | **有，但不是"用 SSO 登录"**：授权中心文档里列了 **密码模式（Password）** —— "应用把账密发给 Authing，账密正确即返回 token"。它揭示了**授权中心可以在没有浏览器会话的情况下，用一次 HTTP 直接换 token**。若该应用开启了 `password` grant，多账号并行在原理上就成立了（§3.3.1，含四个前置条件）。**这是 30 分钟就能验完的一条路**。 |
| "密码还没填充就点击登录"的根因是登录方式吗？ | **不是。** 它与"账密 / AD / SSO"三选一无关，是**填表编排的时序问题**。换 SSO 只是把"填表卡住"换成"SSO 卡在跳转/回调"，风险面甚至更大（见 §4）。 |
| 我的建议 | **保留账密通道**，两条并行走：**① 立刻修填表编排的时序缺陷（小改动、可控）；② 中期做"token 直取 + 注入"——优先走平台自己的登录接口，SSO 密码模式作为备选**。SSO 授权码通道**不作为登录通道**。 |
| ⚠ 一个要先打招呼的运营风险 | 策略里"**是否自动跳转**"一旦开启，**进登录页就自动跳 SSO**，账密填表链路整体失效，而扩展**不会报错**（只会找不到表单然后 `stand-down`）。真要开这个开关，扩展侧必须先加"检测到自动跳转 ⇒ 明确告知用户"的分支。 |

## 1. 压倒性的约束：多账号并行是刚需（你已确认）

这一条决定了后面所有分析。本扩展解决的**不是**"打开一个登录页"，而是：

> **同一个浏览器窗口里，对同一个 origin 并行在线多个账号，且账号间呈现层与网络层全链路隔离**（七个隔离平面）。

平台侧恰好支持这件事 —— 且这是**平台给的红利**，不是我们绕出来的：

| 平台事实 | 出处 | 对多开的意义 |
|---|---|---|
| 无状态 JWT Bearer 鉴权，`/api/*` 带 `Authorization` 头 | `DESIGN.md` §3.1 | 出口可改头 ⇒ 每个 tab 可持不同身份 |
| **服务端不互踢**（A 的 token 在 B 登录后仍 200） | `DESIGN.md` §3.2 | N 个 token 并行有效 |
| `isEnableSingleDeviceLogin: False`（平台 JWT 实测值） | `CHANGELOG.md` v3.7.2 | 排除了单设备互踢 |
| 前端失效自检（清 Cookie token 即跳登录页） | `DESIGN.md` §3.3 | 所以**永不删真实存储**，改为每 tab 虚拟视图自洽 |

**⇒ 平台允许"一个人同时是多个身份"。SSO 与 AD 不允许"一个浏览器同时是多个身份"。** 这就是全部矛盾所在。

## 2. 现状链路（先把"登录"到底发生在哪里说清楚）

```
管理页/轮盘点「打开」
  → parallelSession.open(accountId)                         [parallel-session.ts]
      · 无活绑定页签 → 清残留快照（staleCleared）
      · 取 scheme（http/https 数据化）→ URL = scheme://host/login
      · chrome.tabs.create(url)  + 绑定表 + pushBind(种子)
      · 取云端明文口令 → setPendingAutoLogin(tabId, user, pass)   ← storage.session，60s TTL
  → 内容脚本 auto-login.ts 在 document_idle 就绪
      · 向 background 索取凭据（按 tabId）
      · runTopFrameFlow()：
          填「用户名」（顶层） + 填「密码」（★ 同源 srcdoc iframe 内）+ 勾选协议
          → 五重门控通过 → button.click()
  → 平台签发 JWT → 写入 localStorage.__auth_token__ / __auth_user__ / __device_fp__
  → shield-main.ts 捕获写入事件 → 桥 → captureToken()        [parallel-session.ts:251]
      · JWT 形态校验 → 身份护栏 → 存 chrome.storage.session
      · 首次捕获 → snapshotLoginCookies()（登录时点全量快照，含 HttpOnly）
      · syncAccountRules() → DNR 规则热替换（此后本 tab 所有请求带该账号 Bearer）
```

**关键脆弱点（为什么"填表"天然不可靠）**：

| # | 事实 | 后果 |
|---|---|---|
| ① | 密码框在**同源 `srcdoc` iframe** 内，而 `<all_urls>` **不注入** `about:srcdoc` frame | 无法"iframe 各填各"，只能顶层跨 realm 直填（`auto-login.ts` 文件头注释） |
| ② | 该 iframe 的文档加载/重渲染**没有任何对外事件**，只能靠 800ms 轮询 + MutationObserver 猜 | 时序竞态的结构性来源 |
| ③ | 表单是 React 受控组件，重渲染会**清值** | 填充与点击之间随时可能被清 |
| ④ | 登录页 2023 年的构建（截图页脚 `版权所有 © 2023 Akso eGMP`），改版无通知 | 任何选择器/时序假设都会静默失效 |

> **⇒ 结论：只要"登录"的完成动作发生在 DOM 层（填表 + 点击），这条链路就永远有竞态。**
> 这不是当前实现写得不好，是**架构位置选错了**。这一点是后文所有建议的出发点。

| `vpn-c-success.png` | — | — | 登录成功（进入工作台首页「我的待办」） |

> ★ **脱敏口径**：上面三张图是**真机联调截图**，含**真实账号名与客户单位名称**。
> 它们位于 `tmp/`（gitignored ⇒ **不入库**），本文只引用文件名、**不复述真名**

★ 也就是说：**"密码还没填充就点击登录了"不是用户的错觉，现场留下了物证** —— 那个红框
就是空密码提交的直接后果。这解释了用户看到的现象，也把问题锁定在**"填充与提交之间还有一个窗口"**。

而 `auto-login.ts` 里**恰好**有一处专门防这件事的代码（`:284-295`）：

```ts
if (!fillAll()) {
  report('click-aborted', { attempts, reason: 'fields-reset' });
  return;                       // 点击落地前字段被重渲染清掉 → 放弃本轮
}
...
if (!btn || !u || u.value !== credentials!.username || readPasswordValue() !== credentials!.password) {
  report('click-aborted', { attempts, reason: 'readback-mismatch' });
  return;
}
```

⇒ 代码**已经知道**这个窗口存在（`fields-reset` / `readback-mismatch` 两个原因就是为它写的），
但它是**事后检测**而不是**根治**：检测到不一致时只是"放弃这一轮"，窗口下次还在。
**同一族竞态还有第二个形态**：值在"本次回读通过"之后、POST 真正发出之前被框架清掉 ——
那是回读也拦不住的。

> 附带一个**安全含义**（本仓规则 3 的邻域）：空密码提交在平台侧会留下一条失败登录审计。
> GMP 场景下"某个账号存在多次空密码登录尝试"是**看得见的痕迹**，值得在给用户的手册里
> 说明成因，避免被误读为有人在试探口令。

## 3. 逐条评估：三种登录方式

### 3.1 方式一：基础账密登录 —— 现状，保留

已实现（v2.1 起，v3.10.7 加五重门控）。优点：**身份基准是"每账号一份凭据"**，天然支持 N 个账号并行，且与七平面隔离完全兼容。缺点：见 §2 的四条脆弱点。

### 3.2 方式二：AD 域登录

| 维度 | 评估 |
|---|---|
| 身份基准 | **Windows 登录会话**（Kerberos/NTLM/IWA 返回"当前登录的域用户"） |
| 多账号并行 | **理论不可行**。一个 Windows 会话 = 一个域身份，**没有"选人"的入口** |
| 唯一绕过 | 每账号一个 Windows 账户 + 一个独立 Chrome profile ⇒ 回到 v3.9.2 已整体删除的"桌面伴随进程/多 profile"路线（`PROJECT-STATUS.md` §一），与"纯扩展"约束冲突 |
| 扩展侧附带障碍 | SSO/AD 回调发生在**跨域 IdP**，DNR 作用域（`tabIds + requestDomains`）覆盖不到；身份写进**真实 cookie jar**，而会话卫生三层防线会主动驱逐"命中快照的写 jar 行为"（`evictJarCookie`，带归属门控）⇒ 可能把刚建立的 IdP 会话清掉 |
| 结论 | **不作为候选**。除非"AD 策略"实际是"填 AD 账密到平台自己的表单"（那就退化成方式一的变体，见 §3.4 判别方法） |

### 3.3 方式三：单点登录策略（SSO）——★ 已拿到策略配置，机制已确定

**证据来源**（用户提供，2026-10-12）：`单点登录安全策略配置.md` + 授权中心《Oauth2.0》文档截图。

| 配置项 | 实配值 | 含义 |
|---|---|---|
| 策略类型 | **OAuth2.0 策略** | 标准 OAuth2/OIDC 委托 |
| 是否自动跳转 | 可开（开启后**进登录页就自动跳 SSO**） | 可被平台管理端改成"完全绕过账密" |
| 绕过后门 | 登录路径加 `isadmin=true` 可绕过 SSO | 有管理侧逃生口 |
| 授权类型 | **AuthorizationCode** / `authorization_code`，响应类型 `Code` | 授权码模式 |
| 授权中心基地址 / 授权地址 | 授权中心地址 + 跳登录页的路由 | **外部授权中心（Authing）** |
| Token 端点 / 用户信息端点 | 路由地址（配置项） | 服务端换票用（步骤 5） |
| 应用 ID / 应用密钥 | 授权中心创建的应用 | **client_secret 在平台服务端，浏览器拿不到** |
| Scope | `openid username` | OIDC |
| 回调地址 | `http://test.aksoegmp.com/sso-login?*`（移动端 `/mobile/sso-login?*`） | 回到**平台自己**的域 |
| 用户作用域名称 | 与授权中心账号字段映射（默认 `username`） | 身份落点 |

**⇒ 判定：这是"跨域 IdP 委托"型 SSO**（§3.4 判别表第 1 行 + 第 2 行的混合：授权中心在外部，
回调落在平台自己域）。流程是教科书式的 OIDC 授权码模式：

```
平台前端 --1 请求 /auth--> 授权中心(Authing)
         <--2 302 重定向到认证页面--
用户 --3 在 Authing 认证并确权--
         <--4 发送授权码--
平台服务端 --5 用 code 换 token（client_secret，服务端）--> Authing
         <--6 返回 AccessToken / IdToken / 可选 RefreshToken--
平台服务端解 IdToken 得身份 → 重定向前端 → 平台自己的会话建立
```

★ **流程里"认证并确权"发生在 Authing 的会话上** —— 这就是断点 A 的确切位置。

对本扩展而言，**它在三个位置同时断裂**：

#### 断点 A：身份基准是"浏览器会话级单一变量"

SSO 的本质是把身份**外包给 IdP 的会话 Cookie**。而 Chrome 一个 profile 只有**一份 IdP 会话**：

```
账号 A 页签 → /login → [SSO 登录] → IdP（建立会话：A 的身份）→ 回调 → token_A ✅
账号 B 页签 → /login → [SSO 登录] → IdP（已有会话！直接返回）→ 回调 → token_A ❌ 还是 A
```

- **tab 级隔离救不了它**：七平面隔离的是 `tonbridge-config.aksoegmp.com` 这个 origin 的存储与出站请求；**IdP 是另一个 origin、写的是真实 jar**，七平面既不覆盖它，也不该覆盖它（那会破坏"扩展不得影响原有网页"的根本原则）。
- **"每次强制重新认证"也救不了**：那等于每开一个账号都手输一次 SSO 凭据 —— 比现在更慢，而且若 IdP 支持多身份并存，就说明它本来就不是"单点"。
- **⚠ 唯一例外**：若平台的 SSO 策略**允许在发起时传"账号/租户标识"，且 IdP 支持多身份并存**，则 A、B 各自可达。**这正是需要你用文件确认的那一点**（见 §6）。

#### 断点 B：扩展会在 SSO 跳转途中**主动解绑**（代码实锤）

跨域 SSO 必然离开授权域。而 `parallel-session.ts::onNavigation` 有一条"授权域护栏"：

```ts
// parallel-session.ts:1296-1302
if (/^https?:\/\//i.test(url)) {
  const host = new URL(url).hostname;
  if (host !== binding.host && !(await isEnforceable(host))) {
    void diag(`onNavigation 非授权域 ${host}：解除 tab=${tabId} 绑定`);
    await this.unbindTab(tabId);
    return;
  }
```

`isEnforceable(host)` = `chrome.permissions.contains` 实查（`:123`）—— **IdP 域名从未被授权** ⇒ 判定为"非授权域" ⇒ **解绑该页签**。

解绑的连锁后果（`:976-991` + `:538`）：
- DNR 规则被摘（网络平面失效）
- `pushDown({op:'unbound'})`（MAIN 壳退回直通，存储命名空间不再接管）
- **若它是该账号最后一个绑定页签 → `terminateLoginState()`：清 token / 清 Cookie 快照 / 清 authUser**

⇒ 你带着 SSO 票据回到平台时，**这个页签已经不再是"账号 B 的页签"了**：它没有隔离、没有种子、没有规则。SSO 建立起来的会话落进**真实 jar + 真实 localStorage**，成为一个"原始页签"。紧接着：
- 平台身份进入**全 profile 共享**状态 ⇒ 其他账号页签的呈现层被污染（这正是七平面要防的那件事）
- 会话卫生层可能驱逐这次 SSO 写进 jar 的平台 Cookie（`evictJarCookie`）

**这不是"改一行白名单"能补的**：要放行 IdP 域，就得回答"哪些域算 IdP"（配置化 + 用户授权 + 多租户 `<租户>.aksoegmp.com` 形态）、"放行期间账号种子与身份头会不会流向 IdP"（`pushBind` 的种子是按 host 下发的，放行 IdP 就等于把 `__auth_token__` 暴露给 IdP 域）、以及"回调回来时按什么判定它还是原账号的页签"。**每一条都是安全边界问题，不是功能问题。**

#### 断点 C：无头/静默 SSO 不可行

若想"不弹 IdP、静默拿 token"，唯一形态是 IdP 支持静默重认证（`prompt=none` / Kerberos 静默）——**那又回到"一个 Windows/IdP 身份"**，即 §3.2 的死路。

#### 3.3.1 ★★ 授权中心的六种模式与本场景的映射（**这一节给出了新机会**）

授权中心文档把 OAuth2 的六种模式列全了。逐个对到"多账号并行"上：

| 授权中心列出的模式 | 文档原话 | 对多账号并行的判定 |
|---|---|---|
| **授权码模式**（Authorization Code） | 需安全存储 `client_secret`，"**必须有后端**" | **这是平台现用的模式**。换票在**平台服务端**做 ⇒ 扩展既拿不到 `client_secret`，也不该拿。❌ 断点 A |
| 授权码 + PKCE | 适用 SPA / 原生应用 | 仍需 IdP 交互式会话 ⇒ ❌ 断点 A（PKCE 只解决"公共客户端不能存 secret"，不解决"一个浏览器一个身份"） |
| **客户端凭证模式**（Client Credentials） | 服务器间（M2M）通信、"**非人参与的场景**" | ❌ 拿到的 token **不代表任何用户身份** ⇒ 无账号可言 |
| 隐式模式（Implicit） | 不推荐，Token 经 URL 传递 | ❌ 且仍是交互式会话 |
| **密码模式**（Password） | 文档明确列出："你的应用将用户账密发送到 Authing → **账密正确则返回 token**" | ⚠ **唯一在原理上支撑"按账号换 token"的模式** —— 见下 |
| 设备代码模式（Device Code） | 无浏览器或输入受限设备 | ❌ 每账号仍需一次人工在另一设备上确权 |

**★ 密码模式的真正价值不是"让 SSO 可用"，而是它揭示了 token 端点的形态**：

> 授权中心**可以在没有浏览器会话参与的情况下，用一次 HTTP POST 直接换回 token**。
> 前提是授权中心为这个应用**开启了 `password` grant**，且扩展知道 `client_id`。

如果这条成立，流程会变成：

```
open(账号 B)
  → POST {Token端点}  grant_type=password&username=B&password=***&client_id=***
  → 拿回 AccessToken / IdToken（**完全不经浏览器、不经 IdP 会话、不经 DOM**）
  → 用 IdToken 的 sub/username 与平台账号做映射
  → 复用已有的种子注入机制把平台会话灌进 B 的命名空间
```

**没有跳转 ⇒ 断点 A / B 同时消失。** 但必须诚实列出它的**四个前置条件**（缺一不可）：

1. **授权中心为这个应用开启了 `password` grant** —— 平台文档把它标为"**不推荐**"，生产 GMP 环境很可能已关闭。**这是第一个要验的点。**
2. **扩展需要 `client_id`**（公共客户端，无 secret）。若授权中心把它当机密客户端，密码模式需要 secret ⇒ **扩展侧做不到**（也不该做）。
3. **平台是否只认它自己签发的 token**：按 SSO 流程第 5-6 步，是**平台服务端**用 code 换 token、解 IdToken 得身份、然后"重定向到前端其他页面" ⇒ 平台前端拿到的**很可能仍是平台自签的 JWT**。若是这样，扩展即使从授权中心拿到 AccessToken，**平台也不认** —— 那就必须让**平台**去换票，等于回到"平台接口换 token"（§5.2 的 D 方案）。
4. **安全评审**：让浏览器扩展持有"用账密直接换 IdToken"的能力，会把 SSO 的身份保证降级为"谁有账密谁能换票"。GMP 场景下这**必须经平台方/QA 书面认可**，不能由客户端默默实现。

⇒ **结论：密码模式是"值得花 30 分钟验证、但不要预先投入"的候选**。它的验证成本极低（一条 curl），
而 §5.2 的 D 方案（走**平台自己的**登录接口）不依赖任何 SSO 策略变更，是更稳的那条。

### 3.4 SSO 判别表（已按实际配置判定）

| 判别项 | 你的实际配置 | 结论 |
|---|---|---|
| 是跨域 IdP 委托还是平台内策略？ | 授权中心（Authing）＝**外部**，回调落平台自己域 | **跨域 IdP 委托** ⇒ ❌ 断点 A + B 同时命中 |
| 授权模式？ | `AuthorizationCode` + `authorization_code`（`client_secret` 在服务端） | 服务端换票 ⇒ 扩展侧无可复用通道 |
| 能否传"账号标识"？ | 配置项里**没有**任何账号/租户入参 | ❌ 无法"以指定身份换票" |
| IdP 是否支持多身份并存？ | 配置未涉及；**取决于 Authing 侧** | ⚠ 唯一未定项（但即便支持，也需人工在 Authing 切身份） |
| 是否有平台自建换票接口？ | 未见文档；`DIAG-GUIDE` 里的 `Oauth/Login` 是强线索 | ✅ **值得优先验证**（§5.2） |

★ 另有一条**本仓已知的多租户事实**会影响"若真要走 SSO"的实现：
`docs/COLLEAGUE-EXT-REVIEW.md:99` 记录平台按 `<租户>.aksoegmp.com` ↔ `<租户>-config.aksoegmp.com`
组织域名，而 QL 目前**只认 `tonbridge-config`**（硬编码，`CODEBASE_OVERVIEW.md:371`）；
配置文档里的回调示例是 `test.aksoegmp.com`，真机截图里租户是一家**制药企业**（名称为脱敏起见不在此复述）。
⇒ 一旦把 IdP 域/租户纳进白名单，就必须**数据化**而不是再写死一个域名（v3.10.9 的 scheme 教训同族）。

★ **还有一个必须提醒的运营风险**：策略里"**是否自动跳转**"一旦开启，
**进登录页就自动跳 SSO** ⇒ 账密通道会被平台自己关掉，这时 `auto-login` 的填表链路**整体失效**，
而扩展**不会报错**（它只会找不到表单然后 `stand-down`）。若哪天真要开这个开关，
扩展侧必须先加一条"检测到自动跳转 ⇒ 明确告知用户而不是静默停手"的分支。

## 5. 建议的两条路（都不依赖 SSO）

### 5.1 立刻做：修填表编排的时序缺陷（E）

不改登录方式，只把"填表→提交"的编排从**猜时序**改成**看事实**：

| # | 现状 | 问题 | 改法 |
|---|---|---|---|
| ① | 密码框就绪只能靠 800ms 轮询 + MutationObserver 猜 | 竞态窗口 | 以**可观测事实**为门槛：`iframe` 的 `load` 事件 + 密码框 `value` 已落地 + 提交按钮 **enabled**（React 校验通过的唯一可信信号），三者齐备才允许点击 |
| ② | 试次计数与"点击是否真的送达"脱节 | 见下 | 把"试次"记为"**已送达的点击**"，未送达的编排轮次不计入上限 |
| ③ | 用户在填充未完成时手点登录按钮 ⇒ 被判定为"用户接管"⇒ **自动流程永久让位** | 表现就是"看着表单是填好的，但怎么点都登不上" | 把"用户点击"与"用户**修改凭据**"区分开：前者不必然让位，可继续补齐后重试一次 |
| ④ | 失败原因（`click-aborted` 的 `fields-reset` / `readback-mismatch`）只进 `ql:forensics` | 现场看不出来 | 管理页「导出诊断」里显式呈现"上次登录中止在哪一步" |

★ 这一条需要**先做实证**（复现 + 定位到具体分支），不靠推理下结论 —— 见 §7 的进行中验证。

### 5.2 中期做：把"登录"从 DOM 层搬到 API 层（D）——**真正解掉竞态的那条路**

平台的鉴权是**无状态 JWT**。本扩展**已经在做**"token 到手 → 直接注入页面"这件事：

```ts
// parallel-session.ts:1367-1382  buildBindPayload()
seed['__auth_token__'] = snap.token ?? '';   // 有快照 → 直接灌进命名空间
seed['__auth_user__']  = snap.authUser ?? '';
seed['__device_fp__']  = snap.deviceFp;
```

⇒ 也就是说：**"免密切换/免密直达"的机制早就存在，缺的只是"token 从哪来"这一环。** 现在这一环必须由"打开登录页 → 填表 → 人（或扩展）点登录"提供。

把这一环换成 API：

```
open(account)
  → 用账号明文口令 POST 平台的签发端点 → { token, authUser, deviceFp? }
  → 写进账号快照（复用 captureToken 的护栏与持久化）
  → chrome.tabs.create(scheme://host/)     ← 直接开首页，不开登录页
  → pushBind(种子) 把 token/user 在页面脚本前灌进命名空间
  → 页面自举即已登录（平台自检通过，因为呈现层状态自洽）
```

**收益**：零 DOM 依赖、零时序竞态、登录耗时从"秒级 + 不确定"变成"一次 HTTP"。

**代价与前置条件（必须逐条确认，不能跳过）**：
1. **签发端点是唯一未知量** —— 需要你从一次真实登录的 Network 里把它抓出来（§6 有取证清单）。
2. **是否需要 `__device_fp__` 参与签发**：目前 `deviceFp` 来自**页面自己写 localStorage** 后被扩展捕获（`:1123`），扩展并不知道它是怎么算的。若服务端要求签发时携带该指纹，则必须**逆向它的生成算法** —— 这是本方案最大的技术债风险点。
3. **协议合规/审计**：绕过登录页签发的 token，在平台的登录审计里可能缺乏"经登录页"的痕迹。GMP 场景下这是**要跟平台方/QA 打招呼**的事，不能默默做。
4. **WAF**：直接 `fetch` 平台接口会被 WAF 拦（我实测 `GET /login` 就被判 418 攻击行为）。所以这个请求应由**页面上下文**发出（`world: 'MAIN'`、同源、带完整浏览器指纹），而不是 SW 里的 `fetch`。
5. **降级链必须有**：接口不可用（改版/风控/网络）时自动回落 §5.1 的填表通道 —— 否则这个改动会把"偶发登不上"变成"彻底登不上"。

### 6.1 ★ 第一组：验"授权中心是否开着密码模式"（约 30 分钟，成本极低）

前置：从**平台管理端 → 系统设置 → 安全策略 → 单点登录安全策略 → Oauth2.0 策略设置**里抄出
**授权中心基地址**、**Token 端点**、**应用 ID**（这三个都是配置项，管理端能看到；**应用密钥不要动**）。

```powershell
# ② 关键一测：授权中心是否允许 password grant
#    把 <账号> / <口令> / <应用ID> 换成真值；口令可先用一个测试账号
curl.exe -s -X POST "<授权中心基地址><Token端点>" `
  -H "Content-Type: application/x-www-form-urlencoded" `
  -d "grant_type=password&username=<账号>&password=<口令>&client_id=<应用ID>&scope=openid username"
```

| 观察到的结果 | 含义 | 处置 |
|---|---|---|
| 返回 `access_token` / `id_token` | **授权中心允许密码模式** ⇒ §3.3.1 的路走通了（还需验第 3 条前置条件：平台认不认这个 token） | 继续 6.2 |
| `unsupported_grant_type` | 该应用未开启 `password` grant | **放弃这条路**，走 §5.2 的 D 方案（平台自己的接口） |
| `invalid_client` | 该应用被当作**机密客户端**（需要 secret） | **放弃**（扩展侧不该持 secret） |
| `403` / WAF 页 | 风控 | 放弃，走 D 方案 |

因为"试过了、不行"和"没试过"在文档上必须能分开 —— 否则下一个人会再试一遍。

## 8. 一句话总结

> **不要把 SSO 当登录通道** —— 你的 SSO 是"外部授权中心（Authing）+ 授权码模式"，身份认的是**这个浏览器在 Authing 的会话**，
> 而 akso-pass 要的是"**这个页签是谁**"。两者天生冲突，硬接还会被扩展自己的授权域护栏**当场解绑**。
> **真正的病根是"登录动作发生在 DOM 层"**。短修是把填表编排从猜时序改成看事实；
> 根治是让扩展自己调**平台的登录接口**拿 token，再用**早就写好的种子注入机制**直接把页面灌成已登录态 ——
> 那条路上没有密码框，也就没有"密码还没填充就点了登录"。
> **唯一值得为 SSO 花时间的地方**是 §6.1 那一条 curl：如果授权中心开着**密码模式**，
> 就能在"不经浏览器、不经 DOM、不经 IdP 会话"的前提下按账号换 token —— 那是 SSO 这条线上唯一的真机会。
