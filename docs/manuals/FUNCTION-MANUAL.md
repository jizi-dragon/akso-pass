# akso-pass 功能手册（用户视角 + 实现思路）

> **它是什么**：一个 Chrome 扩展。让你**在同一个浏览器窗口里**，同时在线**多个**内部低代码平台账号，
> 每个账号一个独立标签页、互不串号，按 `Alt+Q` 一键切换。
>
> 它解决的是一类**看起来像 bug、其实是浏览器机制**的问题：同一个网站的多账号，天然共享
> localStorage / Cookie / HTTP 缓存 / IndexedDB / Service Worker / BroadcastChannel，
> 于是"后登录的把先登录的顶掉""两个账号看到同一份菜单"。
>
> 每一节带 **实现思路**：功能靠什么机制成立、改坏哪条会静默失效。

---

## 0. 为什么需要它（一句话）

平台的登录态不是"一个 token"，而是**六七个平面上的共享资源叠加**。只要有一个平面没隔离，
两个账号就会互相看见对方的身份——而**它不会报错**，只是"数据不对"。

## 1. 功能地图

| 你能做的事 | 入口 | 备注 |
|---|---|---|
| 并行开多个账号 | 每个账号一个标签页 | 核心能力 |
| 一键切换身份 | `Alt+Q` 账号选择器 | 默认快捷键可改 |
| 按"盒子"分组管理 | 选择器里切盒子 | 盒子状态**以云端为准** |

| 批量导入 / 备份迁移 | 设置页 | CSV / JSON |

## 2. 安装与更新

**你要做的**：`chrome://extensions` → 打开「开发者模式」→「加载已解压的扩展程序」→ 选 `dist/`。

**更新后必须点扩展卡片上的「重新加载」** —— Chrome 会缓存扩展的 Service Worker 脚本，
**直接重启浏览器也可能复用旧脚本**。

**实现思路**

- 构建：`npm run build`（esbuild → `dist/`）。
- ★ **三处版本号必须一致**：根 `package.json`、`packages/extension/manifest.json`、`src/shared/constants.ts` 的 `EXT_VERSION`。
  不一致的表现是"装了新版、界面还写旧版"，而没有任何报错。
- 判据：`npm run typecheck` + 三处版本号对比。

## 3. 多账号并行：七个平面

这是全项目唯一的硬核部分。每个账号进独立标签页，扩展在**页面层**把共享资源按账号切开：

| # | 平面 | 用户感受 | 机制 | 位置 |
|---|---|---|---|---|
| 1 | **存储** | 两个账号的偏好设置互不覆盖 | `localStorage` 重定向到 `__ql_ns_<accountId>__`；`document.cookie` 虚拟化成"账号 Cookie 袋" | `content/shield-main.ts` |
| 1.5 | **广播** | 一个账号的操作不会通知到另一个 | `BroadcastChannel` 命名空间化 | `shield-main.ts` |
| 2 | **AUTH** | 每个标签页发出去的 token 是**它自己那个账号**的 | DNR 按 `tabId` 强制改写 `Authorization: Bearer …`（xhr / websocket / sub_frame） | `background/core/tab-rules.ts` |
| 3 | **COOKIE** | 服务端看到的 Cookie 属于正确账号 | 出站 `Cookie` 头按账号**回放**（登录时点采集含 HttpOnly 的全量快照） | `tab-rules.ts` + `parallel-session.ts` |
| 4 | **CACHE** | 不会"刚切的账号显示上一个人的数据" | 同源 GET 追加 `_qlck=t<tabId>`，把共享 HTTP 缓存按标签硬分区 | `shield-main.ts` |
| 5 | **SW / Cache** | 站点脚本缓存不串 | 拦截 `serviceWorker.register` + 注销既有注册；`CacheStorage` 按账号命名空间键控 | `shield-main.ts` |
| 6 | **IDB** | 菜单树 / `isAdmin` 不串（平台把这两样缓存在共享 IDB） | `indexedDB.open/deleteDatabase/databases()` 按账号前缀化 | `shield-main.ts` |

**实现思路（为什么是"页面层"而不是 DNR）**

- ★ 历史事故：v3.3 的缓存平面用 DNR 的 `redirect.urlTransform` 实现——**该字段 Chrome 从未支持**（Firefox 专属），
  且 `updateSessionRules` 是**原子批量**：一条非法 ⇒ 同批的 COOKIE / AUTH 规则全部被拒，**网络平面全死**。
- ⇒ v3.5 起：缓存改为**页面层实现**，规则安装**逐条降级**（一条失败不影响其它）。
- ★ 纪律：**一个平面没隔离 = 所有平面白做**。加新平面时必须同时回答"它的共享载体是什么、谁在写它"。

## 4. 账号来源：云端账号库

**你会看到**：扩展要你先「用云端账号库登录」——它给出一个码，你去 `https://www.dragonrain.top/authorize` 确认，扩展就登上了。

**实现思路**

- 走 **设备授权流**（`device-start` → 网页批准 → 客户端轮询拿会话），所以**扩展里不需要存你的密码**。
- 账号与口令存在服务端（加密），扩展**只读**。日常增删改在云端控制台做。
- ★ 为什么不让扩展存：扩展是"可被本地改包"的边界，把密码放进去等于把口令交给一台可能被改过的机器。
- 判据：扩展里搜不到任何明文口令字段；断开云端登录后账号列表应为空（不是缓存一份）。

## 5. 账号选择器（`Alt+Q`）

**你会看到**：任意页面按 `Alt+Q`，浮出账号网格；`Esc` / 再按一次 / 点遮罩关闭。

| 快捷键 | 选择器 | 一屏内容 |
|---|---|---|
| `Alt+Q` | 账号 | 一盒最多 20 个账号 |
| `Alt+1` | 常用页面 | 跟随当前账号，在**新标签页**打开 |

**实现思路**

- 打开时**优先落在当前站点关联的盒子**（你在站点 A 的页面里按，就落到 A 的盒子）。
- 浮层需要**站点授权**；没授权时按设计**降级为独立小窗**（不是"没反应"）。
- ★ 这条降级很重要：浮层方案在受限页（`chrome://`、Web Store）根本注入不进去，
  不给降级路径的表现就是"快捷键失灵"，而用户会以为是扩展坏了。

## 6. 盒子管理

**你会看到**：选择器里可以切盒子；盒子能改名、能装账号；有"默认盒子"。

**实现思路**

- **盒子的状态以云端为准**（2026-10-13 起）：本地不维护第二份盒子真相，
  否则"扩展里改了、网页端没变"会变成一次看不见的分叉。
- 盒子与站点关联：一个盒子可以绑一个站点，`Alt+Q` 据此决定默认落在哪个盒子。
- 判据：云端改盒子 → 扩展刷新后一致；本地不产生"只有我这儿有"的盒子。

## 7. 数据与安全（诚实边界）

| 边界 | 说明 |
|---|---|
| **主动提权挡不住** | 把普通用户抬成管理员需要"接管服务端应答"；客户端篡改会导致白屏（无回退渲染）。真正的权限边界应在平台服务端 |
| **Web Worker 里的 IndexedDB** | 不受主世界补丁影响（待观测） |
| **Cookie 快照只在登录时点采集** | 服务端若在会话中轮转会话标识，该账号需重新登录刷新快照（JWT 主体不受影响） |
| 不做的 | 不注入脚本改业务逻辑、不劫持请求做越权、不在本地落明文口令 |

★ 这四条**必须逐条保留**：安全边界写得含糊，等于把"我们没做"说成"我们挡住了"。

## 8. 常见故障

| 现象 | 先查什么 |
|---|---|
| 快捷键没反应 | 当前页是否受限（`chrome://`、Web Store）；是否已被其它扩展占用 |
| 改了代码没生效 | 是否点了扩展卡片「重新加载」；`dist/` 是否重新构建 |
| 两个账号还是串号 | 逐个平面核对（表格见 §3），**先看 IDB 与缓存**——它们最不显眼 |
| 切账号后要重登 | Cookie 快照过期（见 §7） |
